# 1차 리팩토링 품질·안정성 검토

검토일: 2026-11-07. Node 24.21.0, pnpm 12.4.2, Windows 환경에서 확인했다. 실제 사용자 DB·NAS·S3에 접근하거나 배포하지 않았다. DB 스키마, 저장·암호화 포맷, API, 동기화 프로토콜은 변경하지 않았다.

## 1. 발견한 문제와 심각도

| 심각도 | 확인한 문제                                                  | 근거와 영향                                                                                                                                                                                                   |
| ------ | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 높음   | 복구 키 생성 완료가 화면의 민감 정보 초기화보다 늦을 수 있음 | 네이티브 난수 생성이 끝난 뒤 화면 상태를 무조건 갱신했다. 백그라운드 전환·잠금·화면 이탈 뒤에도 완료 결과를 적용할 수 있는 실행 경로를 확인했다. 취소된 비동기 생성 결과를 반환하는 문제를 테스트로 재현했다. |
| 높음   | 내보내기·첨부 읽기 완료와 공유 시작 사이의 권한 검사 공백    | promise가 완료된 뒤 공유 서비스가 이어서 실행되기 전에 세션·카테고리 권한이 만료되는 경우, 평문 파일을 생성하고 공유했다. 백업·첨부 각각 수정 전 실패하는 회귀 테스트로 확인했다.                             |
| 중간   | JSON 공유 중 강제 종료되면 평문 캐시가 다음 실행에도 남음    | 정상 종료의 finally 정리는 있었지만 시작 시 정리 대상에는 JSON 내보내기 파일이 없었다. 시작 시 캐시 목록을 모킹한 테스트로 확인했다.                                                                          |
| 중간   | 백업 가져오기가 파일마다 전체 첨부 descriptor 목록을 재구성  | 파일 수 F, 첨부 참조 수 A에 대해 descriptor 검색이 O(F×A)였다. 큰 백업에서 불필요한 반복과 임시 배열을 만들었다. 데이터 오류가 확인된 것은 아니다.                                                            |
| 낮음   | 기존 서식 경고 2건으로 전체 서식 검사가 실패                 | AGENTS.md의 불필요한 빈 줄과 mobile tsconfig.json의 배열 배치가 Prettier 결과와 달랐다. 규칙 내용과 TypeScript 설정 의미는 문제없었다.                                                                        |

이 심각도는 확인한 실행 경로의 영향에 대한 평가다. 실제 정보 유출이나 사용자 데이터 손실이 발생했다는 의미는 아니다.

## 2. 실제 수정과 이유

- **복구 키 생성:** 선택적 AbortSignal을 받도록 하고 난수 버퍼를 finally에서 지운다. 설정 훅은 이전 요청·화면 이탈·잠금 시 요청을 취소한다. 완료 직전에도 활성 상태, 잠금, 동일 store, 카테고리 권한 버전을 확인한다. 취소 이외의 오류는 계속 전달한다. 기존 키 형식과 SecureStore 저장 경로는 그대로다.
- **백업·첨부 공유:** 비동기 읽기 결과를 받은 직후 권한을 재검사하고, 통과한 경우에만 평문 캐시를 만들고 네이티브 공유로 넘긴다. 이미 승인하여 시작한 공유는 정상 완료까지 파일을 유지하고 finally에서 정리한다. 외부 앱이 파일을 읽는 도중 삭제하는 방식으로 바꾸지 않았다.
- **시작 시 캐시 정리:** 앱 캐시 안의 기존 생성 규칙인 `yeongdu-memo-숫자.json`도 제거한다. 첨부 공유 파일 및 ImagePicker/ImageManipulator 디렉터리 정리는 유지한다. 다른 이름의 파일과 선택한 외부 원본은 삭제하지 않는다.
- **백업 가져오기:** 복원된 blob ID로 descriptor를 한 번 인덱싱한다. 검색 비용을 O(A+F)로 줄이고 파일→복원 객체의 대응을 읽기 쉽게 했다. 가져오기 트랜잭션, 메모·outbox 커밋, 권한 확인, 새 저장 객체 ID, Markdown 원문은 유지했다.
- **서식:** 경고 2건만 포맷했다. AGENTS.md의 빈 줄을 제외한 내용과 tsconfig.json을 파싱한 설정 값이 동일함을 확인했다.

추가 파일 분리나 새 프로덕션 계층·의존성은 만들지 않았다.

## 3. 검토했지만 변경하지 않은 부분

- **LocalStore의 쓰기 큐·원자적 트랜잭션:** 메모·outbox·첨부 저장이 한 경계에 있고 공유 CategoryAccess를 사용한다. 이를 더 나누면 원자성과 권한 상태의 소유권이 흐려지므로 유지했다.
- **동기화·체크포인트·서버 repository:** 기존 테스트와 코드 검토에서 revision/cursor 검증, 사용자 소유 범위, operation UUID 재시도, 충돌 사본 보존, 동기화 중 편집 보존을 깨는 근거를 찾지 못했다. 키 등록·receipt·revision 트랜잭션이나 라우트 경계를 다시 설계하지 않았다.
- **편집기·메뉴·파일 선택·미리보기:** 커서/포커스, 뒤로 가기 저장, 접근 버전 검사, 가공 직렬화와 임시 파일 수명이 서로 연관되어 있다. 자동화 테스트가 확인하는 경계를 유지하고 실기기 항목을 아래에 남겼다. 화면 UI는 바꾸지 않았다.
- **생체 인증 서비스:** 중복 프롬프트 방지, 취소 결과, 실패 전달과 상태 해제가 이미 명확하다. 구현을 바꾸는 대신 회귀 테스트를 추가했다.
- **Dockerfile·Compose:** Node 24 다단계 빌드, 비루트 사용자, read-only 루트, /tmp tmpfs, /data의 DB·첨부 영속 볼륨, healthcheck, SIGTERM 종료 연결을 정적으로 확인했다. .dockerignore는 환경 파일·DB·개발 산출물을 제외한다. 실제 컨테이너에서 확인되지 않은 가정을 이유로 설정을 바꾸지 않았다.

추가한 13개 테스트는 다음 경계를 보호한다.

- 취소된 키 생성 결과 폐기·바이트 초기화, 네이티브 난수 오류 전달: 2개.
- 백업 완료→공유 직전 권한 만료: 1개.
- 첨부 완료→공유 직전 권한 만료, 승인된 공유가 끝날 때까지 파일 유지: 2개.
- 실제 파일 기반 SQLite WAL 트랜잭션 중 자식 프로세스 강제 종료: 1개. 커밋 전 첨부 조각 쓰기 경계에서 중단하고 다시 연 DB의 메모·outbox·암호문 캐시·메타데이터·첨부 테이블을 기존 스냅샷과 비교했다. integrity_check도 확인했다.
- 서버가 조각을 받은 뒤 응답 유실→로컬 DB 재개방→재전송: 1개. 같은 operation UUID·암호문 캐시를 유지하고 재암호화하지 않으며 상대 기기에서 원래 바이트를 읽는다.
- 여러 파일과 공유 blob을 포함한 백업 가져오기: 1개. 새 저장 blob ID와 기존 논리적 참조, Markdown 원문과 파일 바이트를 확인한다.
- 기기 인증 미등록·중복 요청·취소·네이티브 오류·재시도: 3개.
- 시작 시 중단된 공유 캐시 정리 및 외부 원본 삭제 방지: 2개.

기존 테스트는 네트워크 실패·중복 요청·충돌·체크포인트 불일치·복원 검증 실패·트랜잭션 롤백을 계속 검증한다. 검증을 약화하거나 테스트를 건너뛰지 않았다. 전체 테스트 중 자식 프로세스 실행은 샌드박스의 OS 사용자 정보 조회 제한으로 실패해 승인된 일반 실행 환경에서 다시 실행했다.

`node scripts/smoke-production.mjs`는 OS 임시 디렉터리와 임시 계정을 사용했다. CLI 계정 생성, 암호화 첨부 업로드/다운로드, 동기화 보호, DB+blob 백업 검증/복원, 서버 재시작 영속성, 세대 갱신을 확인했다. 컨테이너 테스트를 대체하지 않는다. Expo export는 JS 번들 확인이며 네이티브 Development Build의 성공을 뜻하지 않는다.

## 5. iOS·Android 실기기 체크리스트

- [ ] 생체 인증 미등록·취소·연속 실패·기기 암호 폴백을 확인한다. 중복 프롬프트가 없고 실패 후 재시도할 수 있어야 한다.
- [ ] 복구 키 생성 직후 백그라운드 전환·잠금·화면 이탈·복귀를 반복한다. 지연된 완료 결과가 키·비밀번호 입력란과 안내창을 다시 노출하지 않아야 한다.
- [ ] 백업 내보내기·첨부 읽기 도중 잠금·카테고리 권한 만료를 발생시킨다. 승인 전 공유는 중단되고, 이미 시작한 네이티브 공유는 파일을 읽고 완료할 수 있어야 한다.
- [ ] 공유 취소·실패 후 임시 파일 정리를 확인한다. 공유 중 강제 종료한 뒤 재실행하면 앱이 만든 JSON·첨부 캐시를 정리하고 선택한 원본은 보존해야 한다. 외부 앱에 저장한 사본은 별도 확인한다.
- [ ] 사진/문서 선택 취소, 선택 도중 백그라운드 전환, 보호 카테고리 재인증 취소를 확인한다. 늦게 돌아온 파일을 잠긴 메모에 삽입하지 않아야 한다.
- [ ] 한국어 조합 입력·긴 메모·키보드·사진 삽입 이후 커서/포커스, 뒤로 가기, 저장 실패 후 재시도를 확인한다. 오류 시 원문과 편집 내용이 보존되어야 한다.
- [ ] SQLCipher DB에서 저장·첨부 트랜잭션 도중 실제 앱 종료/재시작과 오프라인 수정→재연결을 확인한다. 키 손실 시 평문 폴백·DB 자동 초기화가 없어야 한다.
- [ ] 백그라운드 화면 가림·최근 앱 화면·테마·접근성 설정에서도 민감 정보가 노출되지 않는지 확인한다.

위 항목은 네이티브 API 모킹이나 Node SQLite 테스트로 완료 처리하지 않았다. 이번 변경은 JS/TS에 한정되며 네이티브 모듈·플러그인 설정을 바꾸지 않았다. Windows 환경에서 iOS 네이티브 빌드는 실행하지 않았다.

Docker Engine이 있는 환경에서는 **기존 NAS 데이터와 분리한 테스트 볼륨**으로 이미지 빌드, Compose 기동/healthcheck, 비루트 볼륨 쓰기 권한, 재시작·컨테이너 재생성 후 영속성, 정상 종료, DB+첨부 백업·복원을 확인해야 한다. 실제 S3 연결도 이번 검증 범위 밖이며 기존 SDK 모킹 테스트만 실행했다.

## 6. 남아 있는 위험과 운영 주의

- 자동 저장의 기존 400ms 지연 동안 아직 커밋되지 않은 입력은 OS의 즉시 종료 시 잃을 수 있다. 이번 강제 종료 테스트는 커밋된 데이터 보존과 트랜잭션 원자성을 확인하며, 모든 키 입력의 영구 저장이나 네이티브 SQLCipher 복구를 보장하지 않는다.
- 네이티브 공유에 넘긴 평문은 외부 앱·OS 파일 제공자의 수명 정책을 따른다. 앱에서 외부 사본을 회수할 수 없다. 강제 종료 직후 남은 앱 캐시는 다음 시작 때 정리되며 안전 삭제를 보장하지 않는다. JS 문자열의 물리적 메모리 초기화도 보장할 수 없다.
- 훅의 화면 이탈 처리, OS 인증·공유·파일 선택·키보드 동작은 코드 검토 및 모킹된 경계 검증에 더해 위 실기기 확인이 필요하다.
- 이번 변경에 새 DB 마이그레이션이나 프로토콜 배포 순서는 없다. 기존 DB v4·로컬 v3·동기화 v4의 호환 정책과 복구 절차를 그대로 따른다. 기존 운영 DB와 첨부 저장소를 함께 백업하는 절차는 유지한다.
- 자동 파일 GC, 키 교체, 이력 정책, 저장소 이전은 이번 범위에서 변경하지 않았다. Docker·실제 S3·실기기 미검증을 해소하기 전에는 NAS 배포 검증이 끝났다고 볼 수 없다.
