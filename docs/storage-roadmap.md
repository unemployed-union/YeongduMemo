# 첨부파일·수정 이력 도입 조사

2026-11-07. 첨부 기능은 이후 사용자 요청으로 구현했으며 현재 동작은 [첨부 사용법·저장소 운영](attachments.md)을 따른다. 아래 첨부 항목은 후속 확장을 포함한 도입 당시 조사다. 수정 이력은 구현하지 않았다. 현재 메모 payload는 SQLCipher에 원문, 서버 SQLite에는 E2EE 암호문으로 저장한다. `changes`는 증분 동기화 로그이며 사용자용 버전 기록이 아니다. 영구 삭제는 해당 과거 payload와 receipt도 tombstone으로 교체한다. checkpoint 토큰은 이 정리 때 바뀌면 안 된다.

## 첨부파일 권장 구조

- 바이너리는 DB의 거대한 base64 필드 대신 사용자별 불투명 blob UUID를 가진 별도 저장소에 둔다. 원본 이름·MIME·크기·참조 관계는 암호화된 manifest에 저장한다. 경로는 서버 생성 ID만으로 구성하고 모든 API·DB 조회에 소유자 범위를 넣는다. 계정 간 평문 해시 기반 중복 제거는 정보 노출 때문에 피한다.
- 기기에서 파일별 무작위 데이터 키로 암호화하고 계정 키/epoch로 그 키를 감싸는 방식을 권장한다. 대용량 스트리밍은 청크별 AEAD와 고유 nonce, 사용자·blob·청크 순서·총 길이·버전/epoch AAD를 검증한다. 최종 manifest 검증 전에는 완료로 노출하지 않는다. 서버에 파일 키나 평문 이름을 보내지 않는다. 현재 문자열 AEAD API를 그대로 대용량 파일 전체에 적용하지 않는다.
- 임시 업로드 → 청크 검증 → manifest/참조 확정 단계를 멱등 UUID로 처리한다. 로컬 첨부 metadata와 outbox는 같은 트랜잭션에 기록한다. SQLite 커밋과 파일시스템 rename은 하나의 트랜잭션이 아니므로 재시작 시 정리 가능한 staging/commit 상태가 필요하다. 불완전 업로드와 재시도·앱 종료·오프라인 사본도 검증한다.
- 서버에는 blob 소유자·불투명 위치·암호문 크기·상태와 참조/삭제 시점을 보관할 별도 테이블, 로컬에는 업로드 작업·캐시·참조 manifest 마이그레이션이 필요하다. 메모/이력의 참조가 남은 blob을 지우지 않는다. 사용자별 용량·개별 파일 크기·임시 업로드 만료·다운로드 인증·디스크 부족 동작을 정한다.
- 삭제는 tombstone과 유예 기간을 둔다. 오프라인 기기·충돌 사본·휴지통·수정 이력·백업이 참조하는 파일의 보존 범위를 먼저 정의한다. 백업에서 파일이 사라지는 시점과 실제 안전 소거는 구분한다. 임시 평문 미리보기와 공유 파일의 생성·접근·만료도 관리해야 한다.
- 백업은 SQLite 온라인 스냅샷이 참조하는 **불변 암호화 blob manifest와 실제 파일을 함께** 보관한다. 백업 중 GC를 보류하거나 참조 스냅샷을 pin한다. 복원은 모든 blob 존재/무결성 확인 후 DB 세대를 바꿔 공개한다. DB만 복원하면 첨부가 누락되므로 기존 백업 CLI를 확장해야 한다.

## 수정 이력 권장 구조

- 동기화 `changes`와 별도인 불변 revision snapshot 테이블을 권장한다. 각 snapshot은 사용자·note·version UUID·key epoch·서버 순서를 가지며 제목·본문·당시 분류 등은 E2EE payload로 둔다. 현재 메모를 편집할 때만 기존 outbox 경로로 새 변경을 만든다. 과거 버전 ‘복원’은 과거 revision으로 되감지 않고 새 작업/필요하면 새 사본으로 저장한다.
- 원문 snapshot부터 시작하면 Markdown을 손상시키지 않고 검증이 쉽다. diff/압축은 나중에 선택한다. 서버가 평문 diff를 계산할 수 없다. 편집 이벤트마다 보관할지, 동기화된 커밋만 보관할지, 자동 저장을 어떻게 묶을지 명시해야 한다. 현재 영구 삭제로 과거 `changes`를 지우는 정책과 충돌한다.
- 이력 조회도 현재 카테고리 보호와 과거 snapshot의 보호를 모두 확인한다. 카테고리 이동·잠금 변경 이전의 원문을 이력에서 우회 노출하지 않는다. 앱 잠금·백그라운드·권한 취소 시 열린 과거 내용도 지운다. 새 테이블에 대한 모든 서버 조회는 사용자 소유 범위를 포함한다.
- 보존 기간·최대 버전 수·사용자 명시적 이력 삭제·휴지통/영구 삭제·충돌 사본의 독립 보존을 정의한다. ‘영구 삭제’ 후 이전 백업까지 즉시 소거할 수 없음을 안내한다. 키 교체를 도입하려면 옛 snapshot과 백업을 읽을 키 epoch 정책이 먼저 필요하다.
- 서버/로컬 스키마, 증분 수신 계약, history용 cursor 또는 같은 change stream의 typed event와 구버전 차단, 백업 CLI의 새 테이블 포함·복원 검증이 필요하다. change/receipt 압축을 도입할 때는 checkpoint와 멱등 재시도 보존 조건도 다시 설계한다.

## 결정 시점

| 시점              | 결정할 사항                                                    | 추천                                                                              |
| ----------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| NAS 배포 전       | RPO/RTO·백업 주기·보존·NAS 밖 암호화 사본·복구 키 담당자       | DB+JSON+키를 별도 보관하고 복사본 복원 연습을 출시 조건으로 둔다                  |
| NAS 배포 전       | 서버 저장 위치·단일 writer·디스크 여유·모니터링                | 로컬 FS의 SQLite, 무기한 change/receipt 증가량과 자동 마이그레이션 백업 용량 감시 |
| NAS 배포 전       | 모든 기기 업그레이드·이미 동기화한 구버전 DB의 수동 복구       | 원본 유지, 별도 공간에서 사본 가져오기. cursor 초기화 금지                        |
| NAS 배포 전       | ‘영구 삭제’와 백업 잔존 정책                                   | 사용자에게 백업/오프라인 사본/충돌 사본까지 자동 소거되지 않음을 안내             |
| 기능 개발 시작 전 | 첨부 크기/총량·유예 기간·백업 일관성, 이력 보존·삭제·보호 기준 | E2EE manifest+불변 blob, 별도 암호화 snapshot. 마이그레이션 전에 정책 확정        |
| 기능 개발 시작 전 | 키 epoch·오프라인 기기 지원 기간                               | 안전한 키 교체를 제공하려면 기기 등록·이중 읽기·백업 구키 보존 정책 선행          |
| 나중              | 첨부 UI·파일 종류 확대·썸네일·캐시 크기, 이력 타임라인·diff UI | 보존·권한·복원 경계가 정해진 다음 개선                                            |

현재 첨부는 서버 v4·로컬 v3 마이그레이션과 E2EE 조각 저장을 사용한다. 자동 GC와 파일별 키 wrapping/키 epoch는 후속 설계이며 원본 암호문을 보수적으로 보존한다. 사용자용 수정 이력 테이블은 아직 만들지 않는다.
