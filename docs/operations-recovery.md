# NAS 배포 전 백업·복구 절차

2026-11-07 구현 기준. 현재 서버 스키마 v4·로컬 v3·동기화 v4이며 첨부가 추가되었다. [첨부 저장소의 백업·복원](attachments.md)도 함께 따른다. 이 문서의 운영 명령은 관리자가 검토한 후 실행하는 절차이며, 이번 작업에서는 사용자 DB·NAS에 접근하거나 배포하지 않았다. 실제 복구 전에 **복사본과 별도 앱 데이터 공간으로 연습**한다.

## 보관할 세 가지

1. SQLite 온라인 백업: 사용자·비밀번호 해시·세션·암호문·변경 로그·receipt·서버 식별자와 세대를 포함한다. 로그인 세션도 민감하므로 접근 권한을 제한하고 별도 암호화 보관소로 복사한다.
2. 모든 기기의 JSON 내보내기: 아직 전송되지 않은 수정과 충돌 사본·휴지통·카테고리 보호 정보를 포함한 현재 메모 원문이다. **평문**이며 전송 대기 작업 UUID·삭제 의도·cursor 전체를 대체하지 않는다. 파일을 암호화 보관하고 원본 기기·앱 데이터를 유지한다.
3. 해당 계정의 64자리 복구 키: 비밀번호 관리자와 별도의 안전한 오프라인 장소에 보관하고 값을 확인한다. 서버 백업에는 이 키가 없다. SQLCipher 로컬 DB 키와도 다르며 복구 키로 로컬 DB를 직접 열 수 없다.

복구 지점 목표(RPO), 허용 중단 시간(RTO), 보존 기간, NAS 밖 복사 주기·장소와 복원 연습 담당자를 배포 전에 정한다. 백업 자동 스케줄·암호화 보관소·세션 일괄 폐기 UI는 이번 구현에 포함하지 않는다.

## 마이그레이션과 호환성

- 서버 스키마 **v4**는 첨부 manifest 테이블을 추가하고, 이전 v3의 `sync_identity`와 `changes.checkpoint`를 유지한다. 메모·revision·cursor·세션·receipt를 지우거나 다시 번호 매기지 않는다. v1/v2/v3 파일은 변경 트랜잭션 전에 SQLite backup API로 `DATABASE_PATH.before-v4-UUID.db`를 만든다. 백업 실패 시 마이그레이션을 중단한다. 새 DB에는 이전 백업이 없다.
- `backup` CLI는 원본을 읽기 전용으로 열고 **마이그레이션하지 않는다**. 새 대상 파일만 생성하며 기존 파일은 덮어쓰지 않는다. 생성 직후부터 POSIX 권한 0600을 요청한다. Windows ACL·NAS 공유 권한과 외부 복사본 권한은 운영자가 확인한다. 실패한 새 대상 파일이 남을 수 있으므로 성공 종료·무결성 검증 전에는 백업으로 사용하지 않는다.
- 서버 시작·백업·백업 검증 이외 CLI는 필요 시 마이그레이션한다. 서비스 하나만 DB를 소유하도록 하고 스키마 변경·세대 변경 동안 서비스를 중지한다. 디스크에 DB와 별도 백업을 둘 공간이 필요하다. v4 DB를 구버전 바이너리로 열지 않는다. 롤백이 필요하면 현재 파일 일체를 보존한 뒤 별도 경로의 이전 백업으로 검증한다.
- 로컬 스키마는 v3에서 첨부 조각·재전송 테이블을 추가한다. 기존 `metadata`의 checkpoint와 중단 사유, 원문·outbox·암호문 재전송 캐시는 유지한다.

| 조합                                   | 동작                                                                       |
| -------------------------------------- | -------------------------------------------------------------------------- |
| 새 앱 + 새 서버                        | `/sync/v4/*`에서 checkpoint 검사 후 전송·수신                              |
| 구버전 앱 + 새 서버                    | v1/v2/v3 동기화 경로 426: 앱 업그레이드 필요, 요청 내용 적용 안 함         |
| 새 앱 + 구버전 서버                    | checkpoint 경로 404를 업그레이드 안내로 처리, 메모 전송 안 함              |
| 이미 동기화한 구버전 로컬 DB + 새 서버 | 과거 checkpoint가 없어 자동 신뢰 불가, `legacy_checkpoint_required`로 중단 |
| 동기화한 적 없는 로컬 메모만 있는 기기 | revision·cursor가 0이면 최초 선택 서버를 기록한 뒤 정상 동기화             |

**기존 동기화 기기 업그레이드는 수동 복구가 필요할 수 있다.** 숫자 cursor가 같다는 이유로 서버가 원래 이력인지 판별할 수 없으므로 자동 표식 채택·우회 버튼을 제공하지 않는다. 모든 기기 앱을 함께 업그레이드하고 아래 절차로 원본을 보존한다. 이전 앱은 새 카테고리 보호 기능도 강제할 수 없다.

## 백업 생성과 확인

`DATABASE_PATH`를 복사할 DB 경로로 지정한다. 환경변수는 DB 경로만 포함하며 비밀번호·복구 키를 명령 인수나 환경변수에 넣지 않는다.

```sh
pnpm --filter @yeongdu/server backup /absolute/path/memo-2026-11-07.db
pnpm --filter @yeongdu/server backup:verify /absolute/path/memo-2026-11-07.db
```

컨테이너 실행 중에는 서로 다른 파일 이름으로 생성한다.

```sh
docker compose exec -T server node dist/cli.js backup /data/memo-2026-11-07.db
docker compose cp server:/data/memo-2026-11-07.db ./memo-2026-11-07.db
docker compose cp server:/data/memo-2026-11-07.db.attachments ./memo-2026-11-07.db.attachments
```

실행 중 DB 파일 하나를 일반 복사하지 않는다. WAL에 남은 커밋이 빠질 수 있다. 백업 파일을 별도 검증 디렉터리에 복사하고 SQLite의 읽기 전용 연결에서 `PRAGMA integrity_check`와 `PRAGMA foreign_key_check`를 실행한다. `integrity_check`는 `ok`, 외래 키 검사는 결과 행이 없어야 한다. DB 버전·사용자 수·메모 수·키 식별자·최신 checkpoint도 원본과 비교한다. 본문이나 자격 증명을 로그에 출력하지 않는다. 원래 복구 키를 가진 별도 테스트 앱에서 실제 복호화·휴지통·충돌 사본까지 확인해야 복구 연습이 완료된다.

스키마 변경 직전 백업만으로 장기 보관을 대체하지 않는다. 평문 전환 전 백업·이전 JSON·NAS 스냅샷은 계속 평문일 수 있다. 정상 서비스 DB는 NAS의 로컬 파일시스템에 두고, SMB/NFS 위 SQLite 실행과 여러 서버의 동시 쓰기를 피한다.

## 서버 롤백 검사

서버 DB 식별자와 복원 세대 UUID는 정상 재시작에 유지한다. 사용자별 최신 change 번호와 각 change의 무작위 checkpoint 토큰을 기기 SQLCipher metadata에 기록한다. **push 전에** 서버 검사와 로컬 최소 revision·cursor 검사를 수행한다. push/pull 트랜잭션 안에서도 기기가 기억한 이력 토큰을 다시 검사해 검사 직후 DB 교체도 차단한다. 서버 응답으로 확인한 checkpoint는 ack보다 먼저 기록하고, pull은 메모·cursor·checkpoint를 같은 로컬 트랜잭션으로 적용한다.

| 상황                                              | 판정                                                         |
| ------------------------------------------------- | ------------------------------------------------------------ |
| 정상 재시작                                       | 식별자·세대·이력이 같으면 허용                               |
| DB 전체를 그대로 다른 서버로 이동, URL 유지       | 같은 이력이면 허용. 원본 서버와 동시 운영 금지               |
| 다른 DB로 교체                                    | `server_replaced`                                            |
| 세대 갱신 후 복원                                 | `generation_changed`                                         |
| 관찰한 checkpoint/cursor/revision보다 오래된 백업 | `server_regressed`                                           |
| 오래된 백업에서 번호가 다시 커진 다른 분기        | 기억한 change 토큰이 다르면 `history_diverged`               |
| 오프라인 수정 기기가 복원된 서버에 연결           | 전송 전 중단, 기존 operation UUID·본문·cursor·충돌 사본 보존 |

중단 사유는 기기에 지속 저장한다. 이후 원래 서버가 돌아와도 자동 재신뢰하지 않는다. 로컬 편집·내보내기·JSON 사본 가져오기는 가능하다. 앱은 메인 화면과 설정에서 상황·보존 절차를 안내한다. cursor 초기화·자동 삭제·자동 덮어쓰기·자동 rebase는 없다.

**검사 한계:** 이 방식은 기기가 이미 관찰한 이력의 손실·분기를 검출한다. 모든 기기의 마지막 관찰 이후에 생겼다가 사라진 변경은 판별할 수 없다. 백업에 포함되지 않은 미확인 응답도 보편적으로 알아낼 수 없다. 악의적인 서버에 대한 암호학적 투명성 로그는 아니다. 따라서 관리자가 백업을 의도적으로 복원할 때는 항상 아래 세대 갱신을 수행한다. 기기와 서버가 함께 옛 백업으로 돌아간 경우도 외부 보관한 복구 기록·백업 검증이 필요하다.

## 의도적 서버 복원과 수동 복구

1. 모든 기기의 편집을 마치고 자동 접속을 중지한다. 가능한 각 기기에서 JSON과 복구 키를 보관한다. 보호된 메모 내보내기는 기기 인증이 필요하다. 원본 앱을 삭제하거나 데이터를 초기화하지 않는다.
2. 서버를 중지하고 **현재 DB·WAL·SHM을 한 세트로 별도 디렉터리에 보존**한다. 복원 후보 백업과 섞지 않는다. 현재 서버와 옛 백업 양쪽을 복사본으로 검증하고 어느 이력을 기준으로 삼을지 기록한다. 세션이 백업 시점으로 돌아오므로 과거 토큰이 다시 유효해질 수 있다. 외부 접속을 차단한 복사본에서 세션 폐기·재로그인 절차도 준비한다. 세션 일괄 폐기를 선택하면 해당 DB를 백업한 후 트랜잭션에서 `used_refresh`, `sessions`를 비우는 관리자 정비가 필요하다. 메모·receipt·changes는 지우지 않는다.
3. 정비용 별도 경로에 검증된 온라인 백업을 놓는다. 이전 DB의 WAL/SHM과 절대 섞지 않는다. UID/GID와 디렉터리 권한을 확인한다. Docker 기본 서비스 UID/GID는 1000:1000이다.
4. **HTTP 서비스를 중지한 상태**에서 그 복원 경로를 `DATABASE_PATH`로 지정하고 세대를 갱신한다. CLI는 갱신 전 `.before-generation-UUID.db` 백업을 먼저 만든다. 커밋된 메모·revision·이력·receipt는 유지한다.

```sh
pnpm --filter @yeongdu/server sync:renew-generation
# 빌드 산출물을 사용하는 정비 환경에서는:
node dist/cli.js sync:renew-generation
```

Compose 서비스가 중지되어 있다면 정비용 일회 컨테이너에서 동일 볼륨을 연결한다. 다음 명령은 선택한 볼륨의 DB를 실제로 변경하므로 복사본 연습과 경로 확인 뒤 관리자가 실행한다.

```sh
docker compose run --rm --no-deps server node dist/cli.js sync:renew-generation
```

5. 선택한 DB를 서비스 위치에 두고 HTTPS 접속을 복구한다. 정상 재시작·완전한 DB 이동에는 세대를 갱신하지 않는다. 의도적 백업 복원에는 갱신한다. 기존 기기는 자동 전송을 중단하는 것이 정상이다.
6. **별도 기기 또는 별도의 앱 데이터 공간**에서 최신 앱과 원래 서버 URL·계정·키로 연결한다. 먼저 선택한 서버의 메모를 받는다. 원본 기기를 그대로 유지한 채, 각 JSON을 검토하고 새 사본으로 가져온다. 앱 내부 프로필 전환/DB 복제 UI는 제공하지 않는다. 기존 앱 데이터 삭제로 빈 공간을 만들지 않는다.
7. 새 ID 사본과 서버 메모를 수동 비교한다. 중복·휴지통·충돌 사본은 확인 후 정리한다. JSON은 현재 메모 원문 백업이며 기존 outbox의 영구 삭제 의도·receipt를 복원하지 않는다. 미확인 삭제는 원본 기기와 보존한 DB에서 별도 검토한다. 완전 복구 확인 전에는 원본 기기·기존 DB·백업을 폐기하지 않는다.

서버 URL을 바꾸면 로컬 DB의 서버·계정 바인딩도 달라진다. 이 경우도 원본을 유지하고 별도 공간에서 복구한다. DNS/프록시만 바꾸고 URL과 DB를 그대로 옮기는 이전은 동일 계보를 유지한다. 불명확한 두 계보를 자동 병합하는 기능은 없다.

## JSON 가져오기 계약

설정 → 데이터 보관 → JSON 백업 가져오기. 기존 `format: "yeongdu-memo", version: 1, exportedAt, notes` 형식과 첨부 바이트를 포함한 version 2를 지원한다. 최대 50MiB·10,000개이며 전체 검증을 먼저 수행한다. 이전 내보내기에 카테고리·보호 필드가 없으면 미분류·비보호 기본값을 사용한다. 잘못된 필드·지원하지 않는 버전·파일 내 중복 ID·첨부 누락/해시 오류는 전체 거부하고 위치/요약 오류만 안내한다. 원문이나 파일 경로를 오류에 넣지 않는다. 큰 백업은 첨부 참조와 바이트가 함께 유지되도록 신뢰하는 오프라인 환경에서 분할하거나 서버 DB+blob 백업을 이용해야 한다.

- 가져오는 **모든 메모에 새 UUID**, revision 0과 새 operation UUID를 부여한다. 기존 ID가 있는 경우도 사본으로 만든다. 제목·본문 문자열과 작성/수정 시각·고정·즐겨찾기·보관·휴지통을 보존한다. 파일 안의 충돌 사본 관계는 새 ID로 연결한다. 대상이 파일에 없으면 원래 `conflictOf` 참조만 유지한다.
- `purged` 영구 삭제 표식은 메모로 되살리지 않고 건너뛰며 개수를 보여준다. 휴지통 메모는 휴지통으로 가져온다. 이 방식은 과거 삭제 상태를 기존 서버 메모에 덮어쓰지 않는다.
- 기존 카테고리 이름이 겹치면 `(복원)`·번호를 붙여 최대 40자 안에서 구분한다. 가져온 동일 카테고리의 잠금·숨김은 OR로 합치고 같은 이름의 기존 보호 설정도 계승한다. 기존 메모의 분류/보호를 바꾸지 않는다. 보호된 카테고리 또는 기존 보호 메모가 있으면 별도 기기 인증을 요구한다. 가져온 뒤 접근 권한을 지워 다시 잠근다.
- 확인 화면은 본문 없이 개수·카테고리 이름 변경 수·충돌 ID 수·건너뛴 삭제 표식을 보여준다. 확인 전 DB 변화는 없고, 확인은 한 번만 소비한다. 백그라운드·보호 변경·메모 ID 집합 변경 후에는 다시 검토한다. 일반 본문 편집은 원본을 덮어쓰지 않으므로 유지할 수 있다.
- 모든 사본과 outbox를 한 트랜잭션으로 커밋한다. 한 건 실패하면 전체 롤백한다. 일반 E2EE 동기화 경로를 사용하되 롤백 중단 표식을 해제하지 않는다. 같은 파일을 다시 확인해서 가져오면 사본이 추가되므로 결과를 확인한다.
- 선택한 파일을 수정·삭제하지 않고 추가 평문 캐시를 만들지 않는다. OS/파일 제공자가 선택용 임시 사본을 만들 수 있다(iOS). 원본과 제공자 임시 파일의 보관·삭제 정책은 OS/사용자 책임이다. 외부 파일 선택 중에도 앱 잠금 정책을 유지하고 정상 잠금 해제 후 읽는다. 내보내기 공유용 앱 캐시는 공유 종료 후 정리하지만 다른 앱에 저장한 사본은 그대로 남는다.

## 복구 키 관리와 키 교체 제한

새 연결은 별도 보관한 키를 다시 입력하고 보관 확인을 해야 진행한다. 저장된 키는 서버·사용자·키 식별자로 분리한 SecureStore 슬롯에만 둔다. 조회용 현재 키 식별자도 SecureStore에 둔다. 설정의 ‘저장된 복구 키 확인·보관’은 기기 인증 뒤 같은 계정의 키를 검증하고 보여준다. 새 연결 이후에는 오프라인에서도 확인할 수 있다. 이전 설치는 현재 식별자 인덱스가 없어 원래 계정으로 한 번 온라인 조회가 필요하다. 키가 없거나 손상되면 자동 생성·덮어쓰기하지 않는다. 표시·입력 중인 키는 앱 비활성화·잠금 때 화면 상태에서 지운다. JS 문자열의 물리적 메모리 소거는 보장하지 않는다. 앱이 자동으로 파일·일반 설정·로그·클립보드에 키를 기록하지 않는다.

**키 교체는 구현하지 않았다.** 현재 서버는 계정당 불변 keyId 하나이며, AAD·과거 `changes`·receipt·기기 암호문 outbox·오래된 백업이 기존 키를 참조한다. keyId만 변경하면 오프라인 재전송이 거부되고 옛 백업을 읽을 수 없다. 같은 operation UUID로 재암호화하면 receipt 요청 해시도 달라져 멱등성을 위반한다. 다음 설계가 먼저 필요하다.

1. 키 epoch/여러 키 식별자와 이전 키 보관 방식, 변경 이력·백업의 구키 보존 기한.
2. 기기 등록 목록·폐기/분실 기기 처리와 오프라인 기기 유예 기간, 재연결 시 epoch 전환 절차.
3. 재암호화 대상(현재 메모/변경 로그/receipt/첨부/이력), 중단·재개 가능한 작업과 서버 커밋 경계, 새 작업 UUID와 기존 미확인 요청 처리.
4. 키 유출에 대응하는 회전인지 단순 키 재보관인지, 옛 백업을 보존하면서 유출된 키의 복호화 능력은 철회할 수 없다는 정책.
5. 복원 세대와 키 epoch를 함께 검증하는 프로토콜, 구버전 차단과 실패/롤백 복구 테스트.

현재 ‘최초 연결용 복구 키 만들기’는 신규 계정용이다. 기존 계정의 교체 기능이 아니며 서버는 다른 키 등록을 거부한다. 로컬 DB·오프라인 기기·백업을 모두 자동 재키잉할 수 있다는 가정을 하지 않는다.
