# 사진·파일 첨부와 저장소 운영

2026-11-07 구현 기준. 사용자 DB·NAS·실제 S3 버킷에는 접근하거나 배포하지 않았다.

## 앱에서 사용

편집 화면 아래 **클립 아이콘 → 사진·파일 첨부**를 선택한다. 사진은 원본 크기, 긴 변 2560px, 1280px 중 선택한다. 축소는 비율을 유지하며 작은 사진은 확대하지 않는다. PNG는 투명도를 유지한 PNG, 그 외 축소 사진은 품질 0.85의 JPEG로 저장한다. 애니메이션/Live Photo는 축소 시 정지 이미지가 된다. 원본에는 위치 등 EXIF가 남을 수 있다. 카메라·마이크 권한은 요청하지 않는다. 원본 파일은 수정하지 않는다.

- 파일 하나 최대 **20MiB**, 메모 하나 최대 **64개**. 원본 이미지는 미리보기 메모리 사용을 제한하기 위해 4천만 화소까지 허용한다. 더 큰 사진은 사진 메뉴의 축소 옵션으로 넣는다.
- 본문 커서 위치에 `![이름](attachment:UUID)` 또는 `[이름](attachment:UUID)`를 삽입한다. 다른 Markdown 문자열은 직렬화·변환하지 않는다. 일반 블록 편집에서는 이미지를 본문 안에 표시하며 파일은 이름·크기의 카드로 표시한다. 긴 메모의 원문 편집에서는 첨부 카드를 아래에 표시한다. 링크 문법을 직접 편집해서 본문에 표시되지 않아도 첨부 목록에는 남겨 명시적으로 제거할 수 있다.
- 원본은 그대로 보관하고 표시용 이미지만 최대 1024px로 만든다. 본문에서 화면 가까운 이미지부터 표시하고, 이미지 처리를 직렬화한다. 정지 미리보기이므로 GIF 원본의 애니메이션은 열기·공유로 확인한다. SVG와 기기에서 지원하지 않는 이미지 형식은 파일로 열 수 있다. 외부 이미지 URL을 자동으로 다운로드하지 않는다.
- 파일 열기·공유는 선택한 앱에 **복호화한 평문**을 전달하므로 확인을 요구한다. 사진 선택·축소·미리보기·공유의 앱 캐시 임시 파일은 작업 종료 후 정리하고, 강제 종료에 대비해 다음 시작 때 해당 앱 소유 캐시 경로도 정리한다. OS 파일 제공자·다른 앱에 남은 사본은 자동 삭제할 수 없다. 공유 중에는 다른 앱이 파일을 읽어야 하므로 정상 공유 종료까지 임시 파일을 유지한다.
- 앱 잠금/카테고리 잠금은 첨부 repository 읽기와 미리보기에도 적용한다. 백그라운드·권한 변경 시 이미지 표시 상태를 지우고 늦은 결과를 버린다. 파일 선택 중에도 일반 앱 잠금을 유지하며 잠금 해제 후 처리한다. 보호된 메모는 필요하면 다시 기기 인증한다.
- 오프라인에서도 파일과 메모·outbox를 하나의 SQLCipher 트랜잭션으로 저장한다. 파일 처리/저장 중 편집을 잠시 막아 추가 입력과 경쟁하지 않도록 한다. 파일은 SQLCipher 내부 조각으로 보관하며 로컬 파일 키를 일반 파일에 저장하지 않는다. 업로드는 편집을 마친 뒤 일반 동기화와 함께 진행한다. 새 기기는 이미지 표시 또는 파일 열기 때 파일을 내려받아 오프라인용으로 보관한다.

## E2EE와 동기화

파일은 256KiB 조각으로 나누어 기기에서 AES-256-GCM으로 암호화한다. 계정의 기존 SecureStore 키를 사용하며 AAD에 첨부용 도메인·버전·사용자·keyId·파일 UUID·조각 순서·총 개수를 넣는다. 각 조각은 독립 무작위 nonce를 사용한다. 파일 평문 SHA-256·이름·MIME·크기·해상도는 암호화된 메모 안에 저장한다. 서버에는 파일 UUID·키 식별자·조각 수/암호문 크기·암호문 해시와 소유자만 보인다. 메모 envelope에 첨부 ID 목록을 넣고 AAD와 복호화 결과 모두에서 검증한다. 첨부가 없는 이전 envelope와 미확인 요청의 UUID·암호문·receipt 해시는 바꾸지 않는다.

업로드는 manifest 예약 → 조각 전송 → 전체 저장 검증/완료 → 메모 전송 순서다. 완료하지 않은 파일을 참조하는 메모 전송은 거부한다. 암호문은 SQLCipher의 재전송 캐시에 먼저 기록해 응답 유실·재실행 후에도 동일 ID·암호문으로 재시도한다. 기존 파일 객체 ID의 다른 내용은 덮어쓸 수 없다. 다른 기기에서 받은 파일은 기존 서버 암호문을 검증해 재사용한다. JSON 복구 사본은 본문의 논리적 첨부 ID를 유지하되 암호화된 descriptor의 `blobId`를 새 UUID로 만들어 미완료 업로드 예약과도 충돌하지 않는다. 서로 다른 nonce로 같은 객체 ID를 덮어쓰지 않는다. 다운로드는 전체 조각과 평문 해시를 검증한 뒤 한 트랜잭션으로 보관한다. 충돌 사본도 독립적인 메모와 첨부 참조를 유지한다.

동기화는 **v4**이며 v1/v2/v3 경로는 426으로 차단한다. 모든 기기를 함께 업데이트한다. 새 앱이 이전 서버에 접속하면 업그레이드를 안내하고 전송하지 않는다. 서버 롤백 checkpoint 검사를 파일 전송 전에 수행하고 업로드 API도 witness를 검사한다. 키 교체는 여전히 지원하지 않는다. 현재 파일 키를 포함한 키 epoch/오프라인 기기/백업 재키잉 정책은 후속 설계가 필요하다.

## 서버 디스크

기본값은 파일시스템이며 서버 DB 옆 `attachments` 디렉터리를 사용한다. Docker에서는 기존 `/data` 볼륨 안에 `/data/attachments`를 둔다. 메모 본문을 DB 밖으로 이동하지 않는다.

```dotenv
ATTACHMENT_STORAGE=filesystem
ATTACHMENT_PATH=/data/attachments
ATTACHMENT_QUOTA_BYTES=1073741824
```

계정별 기본 **1GiB** 한도이며 예약/미완료 업로드도 포함한다. 파일은 `사용자UUID/파일UUID/순서-암호문해시.bin`으로 저장한다. 파일 이름·본문·MIME를 경로에 넣지 않는다. 새 파일은 0600, 디렉터리는 0700을 요청하며 Windows ACL과 NAS 공유 권한은 관리자가 확인한다. 임시 파일을 flush한 뒤 기존 대상을 덮어쓰지 않는 링크로 확정한다. 저장 경로의 심볼릭 링크나 공유 쓰기 권한을 신뢰 경계 밖 사용자에게 제공하지 않는다.

## S3·S3 호환 저장소

미리 생성한 **비공개 버킷**을 사용한다. 서버만 SDK로 접속하고 앱에 S3 자격 증명·공개 URL·presigned URL을 전달하지 않는다. 서버 API가 사용자 소유권을 확인한 뒤 암호문만 중계한다.

```dotenv
ATTACHMENT_STORAGE=s3
S3_BUCKET=private-memo
S3_REGION=ap-northeast-2
S3_PREFIX=yeongdu-memo
S3_FORCE_PATH_STYLE=false
# AWS S3는 S3_ENDPOINT를 설정하지 않는다.
# MinIO 등 S3 호환 저장소 예:
# S3_ENDPOINT=https://minio.example.com
# S3_FORCE_PATH_STYLE=true
```

자격 증명은 공식 AWS SDK의 기본 credential chain(서버 IAM 역할·자격 증명 파일·환경변수 등)을 사용한다. NAS에서는 `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, 필요하면 `AWS_SESSION_TOKEN`을 서버 secret 설정으로 공급할 수 있다. 앱의 E2EE 복구 키와는 다른 자격 증명이다. 이미지·저장소·로그에 값을 넣지 않는다. Compose에는 환경변수 전달만 정의했다. endpoint에는 사용자 이름/비밀번호를 넣지 않는다.

선택 prefix의 `s3:GetObject`, `s3:PutObject`와 없는 객체 확인에 필요한 제한된 `s3:ListBucket` 권한을 준비한다. 자동 삭제는 하지 않으므로 DeleteObject 권한은 필요하지 않다. 공개 ACL을 설정하지 않는다. 저장소는 `If-None-Match: *` 조건부 PUT을 지원해야 한다. 이미 있는 객체는 내려받아 바이트가 같은지 확인하며 다른 내용을 덮어쓰지 않는다. AWS 공식 API와 설치된 SDK 타입을 기준으로 구현했고 SDK 모킹 회귀 테스트를 실행했다. 실제 AWS/MinIO의 인증·정책·TLS·용량·장애 상황 검증은 배포 환경에서 별도로 필요하다.

기존 DB를 운영하면서 저장소 종류·bucket·endpoint·prefix를 단순 변경하지 않는다. DB에 저장소 식별자를 기록하므로 설정이 달라지면 기존 파일 접근/백업을 차단한다. 서버 디스크의 경로 이전은 모든 암호문 파일을 함께 복사하고 무결성을 확인해야 한다. 서버 디스크 ↔ S3의 자동 이전 기능은 포함하지 않았다. 필요하면 원본 DB+blob 백업을 보존한 채 별도 마이그레이션을 설계한다.

## DB 변경과 배포

- 서버 DB **v4**: `attachments` 테이블 추가. v1/v2/v3 파일은 변경 전에 `.before-v4-UUID.db` 백업을 만든다. 기존 서버 식별자·세대·change 토큰·revision·receipt·세션을 보존한다. v3에는 아직 첨부가 없으므로 이 사전 백업에는 첨부 sidecar가 필요하지 않다.
- 로컬 DB **v3**: `local_attachments`, `attachment_chunks`, `attachment_uploads`를 추가한다. 기존 메모·outbox·암호문 재전송 캐시·checkpoint를 다시 쓰거나 삭제하지 않는다. 이전 앱으로 로컬 v3 DB를 열지 않는다.
- `expo-image-picker`, `expo-image-manipulator`가 추가되어 **Development Build 재빌드가 필요**하다. JS 업데이트만 적용한 이전 앱에서는 동작하지 않는다. Android APK와 iOS 빌드를 모든 기기에 배포하기 전에 JSON/서버 백업을 보관한다. 이미 동기화한 아주 오래된 기기의 checkpoint 부재는 기존 [수동 복구 절차](operations-recovery.md)를 따른다.

## 백업·복원·삭제 정책

`backup` CLI는 DB 스냅샷과 그 스냅샷이 참조하는 암호문을 함께 보관한다. S3도 원격 객체를 내려받아 동일한 형식으로 저장한다.

```sh
pnpm --filter @yeongdu/server backup /backups/memo-2026-11-07.db
pnpm --filter @yeongdu/server backup:verify /backups/memo-2026-11-07.db
# 결과 두 항목을 함께 보관:
# /backups/memo-2026-11-07.db
# /backups/memo-2026-11-07.db.attachments/
```

sidecar의 `complete.json`은 모든 준비 완료 파일을 검증·복사한 뒤 마지막에 기록한다. marker가 없으면 불완전 백업이다. 미완료 업로드는 존재하는 조각만 포함하며 원본 기기의 재전송 캐시로 이어서 전송할 수 있다. 백업 대상 파일/디렉터리는 새 경로여야 한다. 실패한 부분 파일은 성공한 백업으로 취급하지 않는다. Compose에서는 DB 파일과 `.attachments` 디렉터리 **둘 다** 호스트로 복사해야 한다. `sync:renew-generation`의 사전 백업도 첨부 sidecar를 생성한다.

복원은 서버를 중지하고 현재 DB·WAL·SHM·blob 저장소를 보존한 뒤 수행한다. marker의 파일 크기와 SHA-256을 실제 암호문과 비교하고, 스냅샷의 완료된 manifest가 모두 있는지 검증한다. 파일시스템은 sidecar의 사용자 UUID 디렉터리를 선택한 `ATTACHMENT_PATH` 아래로 복원한다(`complete.json`은 데이터 객체가 아니다). S3는 같은 bucket/endpoint/prefix의 동일 객체 키로 복원한다. 기존 파일과 내용이 다르면 덮어쓰지 말고 별도 위치에 양쪽을 보존해 조사한다. 모든 참조가 복구된 후 DB를 교체하고 세대를 갱신해 공개한다. DB만 복원한 상태로 정상 복구라고 판단하지 않는다.

앱 JSON 내보내기는 첨부 바이트를 포함한 **version 2**를 만든다. 아직 없는 파일은 원래 서버에서 받은 뒤 내보내며, 다운로드·무결성 검증에 실패하면 불완전 백업을 만들지 않는다. 보호된 메모는 인증을 요구한다. 기존 version 1(첨부 없는 메모)도 가져올 수 있다. v2는 누락 파일·중복 ID·내용 해시 오류를 거부하고 메모와 첨부를 한 트랜잭션으로 가져온다. 본문의 논리적 `attachment:` 링크와 Markdown 원문은 보존하고 저장 객체 UUID는 새 사본으로 분리한다. JSON 크기 한도는 **50MiB**다. 더 큰 자료는 서버 DB+blob 백업과 파일별 열기·공유로 별도 보관해야 한다. 평문 JSON과 공유 파일에는 민감한 내용이 포함된다.

현재는 안전한 **자동 GC/물리적 첨부 삭제를 제공하지 않는다**. 첨부 제거·휴지통·메모 영구 삭제는 메모의 참조를 제거하지만 다른 메모·충돌 사본·오래된 기기·백업이 파일을 참조할 수 있어 암호문과 로컬 복구용 조각을 보존한다. 미완료 업로드도 자동 삭제하지 않는다. 원본 메모를 영구 삭제해도 과거 백업/암호문까지 안전 소거했다고 주장하지 않는다. 저장 용량이 줄지 않는 것은 이 보존 정책 때문이다. GC를 도입하려면 기기 유예 기간·이력·백업 보존과 명시적 삭제 절차를 먼저 결정해야 한다.

구현에 참고한 공식 API: [Expo ImageManipulator](https://docs.expo.dev/versions/latest/sdk/imagemanipulator/), [AWS SDK S3 PutObject](https://docs.aws.amazon.com/AWSJavaScriptSDK/v3/latest/client/s3/command/PutObjectCommand/).
